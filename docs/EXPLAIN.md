# Explain モード仕様書(v0.1 ドラフト)

> 3D-MOVIE の 3 つ目のモード。**専門知識が要る「仕組み・違い・理由」を、縦型ショート動画(〜60 秒)で正確に説明する**動画を、AI で半自動生成する。
> 既存の Forge(アセット生成)/ Studio(アニメーション)と同じアプリ・同じ GPU ワーカー・同じライブラリの上に載せる。URL は `/explain`。
> 共通の前提(RTX 3060 12GB、WSL2 + Docker、本人のみ利用、Claude API 使用)は [SPEC.md](SPEC.md) に従う。

---

## 0. 決定事項と背景

### 0.1 狙い

- 「土砂崩れを防ぐ家裏の壁の進化」「何が違うの？(銅線の太さ)」のような、**身近だが仕組みを知らない題材**を 3D で見せる縦型ショートは需要が大きい(参考動画は 2 か月で 1,100 万回再生)。
- 参考にしたチャンネルは更新頻度とジャンルの幅から見て、AI を使った量産体制だと推測される。**同じ速度で回しつつ、内容の正確さで差をつける**のがこのモードの目的。
- 他チャンネルの台本・映像・構成は複製しない。題材は自分で選び、根拠資料から台本を起こす。

### 0.2 参考動画から読み取れる 2 つの作り方

| 型 | 例 | 映像の作り方(推定) | 強み | 弱み |
|---|---|---|---|---|
| **A. 3D 図解型** | 擁壁の進化(石積み → ひび割れ・崩壊 → L 型擁壁 → 基礎を伸ばす) | 単純形状の 3DCG。断面カット、破砕・崩壊シミュレーション、カメラワーク | 構造・比率・因果が正確に描ける。場面間で形が一貫 | 質感・人物の表現は控えめ |
| **B. AI 映像+キャラ型** | 銅線の太さの違い(巻線機、充電ケーブル、銅管を曲げるキャラクター) | 画像生成 → 画像から動画生成(image-to-video)、スタイライズされた案内役キャラ | 見た目がリッチで、ジャンルを問わず速く作れる | 構造の正確さ・場面間の一貫性が崩れやすい |

**方針: 1 本の動画の中で両方を混ぜる。** 説明の核心(構造・断面・力の流れ・比較)は A の決定的な 3D 図解で作り、導入・つなぎ・雰囲気カットは B の AI 映像で作る。案内役キャラは Forge で作った人型を Studio で動かして使い回し、チャンネルの顔として一貫させる(B の弱点である「毎回顔が変わる」を避ける)。

### 0.3 決定事項

| 論点 | 決定 | 理由 |
|---|---|---|
| アプリ内の位置づけ | Forge / Studio に並ぶ **3 つ目のモード `Explain`** | ジョブキュー・Blender レンダラ・ライブラリ・スキーマを共有できる |
| 出力 | **縦型 1080×1920、30fps、15〜60 秒、MP4(H.264 + AAC)** | YouTube ショート / TikTok / Instagram リール共通 |
| 正確さの担保 | **主張台帳(出典つき)+ 自動ファクトチェック + 人の承認ゲート**。承認なしでは書き出せない | このモードの価値の中心。誤りは信用を一度で失う |
| 映像の生成方式 | ショット単位で選ぶ: **3D 図解テンプレート(Blender)/ AI 映像 / 静止画+カメラ移動 / Studio シーン** | 正確さが要る所は決定的な 3D、雰囲気は生成 AI |
| ナレーション | ローカル TTS(**VOICEVOX** を第一候補)。CPU で動き GPU を占有しない | 無料、日本語の品質が高く、音素タイミングが取れて字幕同期に使える |
| 字幕(テロップ) | ffmpeg + ASS 字幕で焼き込み。句単位で自動分割 | 縦型ショートは字幕必須(無音視聴が多い) |
| AI 映像の生成場所 | **ローカル(Wan 2.x / LTX-Video)を既定**。外部 API(Veo / Kling / Runway 等)は **プロジェクト単位のオプトイン** | 既存方針「生成物は外に出さない」を守りつつ、3060 では遅い・画質が足りない場合の逃げ道を残す(→ 11 章の確認事項) |
| 投稿 | MVP は **手動アップロード**(書き出し時にタイトル・説明文・出典・ハッシュタグを生成)。自動投稿は v2 | 誤った動画を自動で公開する事故を防ぐ |

## 1. ゴールと非ゴール

### ゴール
- テーマと根拠資料を入れると、**60 秒の解説ショートが 1 本あたり実働 30 分以内**(待ち時間を除く)で仕上がる。
- 動画内のすべての説明文が **出典つきの主張** に紐づき、あとから根拠をたどれる。
- 構造・断面・力の流れ・比較を、3D 図解テンプレートで **形と比率を指定どおりに** 描ける。
- 案内役キャラ・色・字幕デザイン・BGM をチャンネルとして統一できる(ブランドプリセット)。
- 週 5〜7 本の更新ペースを、RTX 3060 1 枚で回せる(夜間バッチで描画)。

### 非ゴール(当面扱わない)
- 横長の長尺解説動画(10 分以上)。
- 医療・法律・投資など **助言に当たる題材**(誤りの害が大きい)。扱う場合は人による専門確認を必須にする(4.4)。
- ニュース・時事の速報(事実が確定しておらず、ファクトチェックが追いつかない)。
- 実在の人物・企業・製品を本物らしく描く映像。
- 投稿後の分析ダッシュボード(v2 で検討)。

## 2. ユースケース

1. 「なぜ高圧送電線は鉄塔の上で何本にも分かれているのか」をテーマに新規プロジェクト。電力会社の技術解説ページ 2 本と教科書の PDF を資料として追加。
2. リサーチ → 主張台帳が 12 件できる。うち 1 件が「出典に記載なし」と判定され、削除する。
3. 台本(約 330 字、55 秒)が生成される。冒頭のつかみは「何が違うの？」型。言い回しを 2 か所直す。
4. 絵コンテ(9 ショット)が生成される。ショット 4〜6 は 3D 図解テンプレート「断面カット」「比較(左右分割)」、ショット 1 と 9 は案内役キャラ(Studio)、ショット 2 は AI 映像(鉄塔の空撮風)。
5. 生成を実行し、夜間に描画。翌朝プレビューで確認し、ショット 5 の矢印の向きだけ直して再描画。
6. 承認チェックリストを埋めて書き出し。説明欄用に出典リストつきの文面が出る。手動でアップロード。

## 3. 全体パイプライン

```
[1] テーマ・資料入力 ──▶ [2] リサーチ(主張台帳) ──▶ [3] 台本 ──▶ [4] ファクトチェック
                                                                     │
                                ┌────── 人の承認ゲート ①(内容) ◀──────┘
                                ▼
[5] 絵コンテ(ショットリスト JSON) ──▶ [6] ショット生成(並列不可、GPU 直列)
                                         ├ 3D 図解(Blender テンプレート)
                                         ├ AI 映像(ローカル / 外部 API)
                                         ├ 静止画+カメラ移動
                                         └ Studio シーン(案内役キャラ)
                                ▼
[7] ナレーション(TTS、CPU) ──▶ [8] 字幕・BGM・効果音 ──▶ [9] 合成(ffmpeg)
                                ▼
                    人の承認ゲート ②(映像) ──▶ [10] 書き出し(MP4 + 投稿用メタデータ)
```

- [2]〜[5] は Claude API(構造化出力 JSON)。[6] は GPU ワーカー。[7]〜[9] は CPU ジョブ。
- 各段の成果物はプロジェクトに保存し、どこからでもやり直せる(例: 台本を直す → 影響するショットだけ再生成)。
- **台本が変わると、紐づくショット・音声・字幕が「要再生成」になる**(依存関係を追跡する)。

## 4. 正確さの仕組み(このモードの中核)

### 4.1 主張台帳(Claim Ledger)

リサーチ段階で、動画で言いたいことを **1 文 1 主張** に分解して台帳にする。

```jsonc
{
  "id": "clm_07",
  "text": "L 型擁壁は、底版の上に載った土の重さで壁が倒れるのを防ぐ",
  "sources": [
    { "ref": "src_02", "locator": "p.14 図 3-2", "quote": "…底版上の土の重量が転倒に抵抗する…" }
  ],
  "confidence": "high | medium | low",
  "status": "supported | unsupported | disputed | removed",
  "risk": "normal | high"          // high = 安全・健康・お金に関わる
}
```

- **出典は利用者が追加した資料(URL / PDF / テキスト)を優先**。LLM の知識だけで書いた主張は `confidence: low` とし、そのままでは承認できない。
- Web 検索による資料追加は v1(検索結果も「資料」として台帳に残す)。
- `quote` は出典の該当箇所の抜粋。ファクトチェック時に出典本文と照合する。

### 4.2 台本と主張のひも付け

- 台本の各文は 1 つ以上の主張 ID を持つ(つかみ・つなぎの文は `kind: hook | transition` とし、事実を含めない)。
- 主張に紐づかない事実文が台本に入っていたら、警告を出して承認をブロックする。

### 4.3 自動ファクトチェック

- 台本生成とは **別の LLM 呼び出し(反論役)** で、各文について次を判定する。
  - 出典の抜粋で裏づけられるか / 言い過ぎ(「絶対」「必ず」「最強」)がないか / 単位・数値の誤り / 因果の取り違え / 一般化しすぎ。
- 3D 図解の **見た目の主張** も検査する(例: 「底版は壁より土側に長い」「矢印は土圧の向き = 土側から壁へ」)。絵コンテの各ショットに `visual_assertions` を持たせ、チェックリストとして人が確認する。
- 結果は文ごとに `ok / 要修正 / 根拠不足` の 3 段階で表示する。

### 4.4 承認ゲート

| ゲート | 確認すること | 必須条件 |
|---|---|---|
| ① 内容 | 台本の全文、主張台帳、ファクトチェック結果 | `根拠不足` が 0 件。`risk: high` の主張は人が出典を開いて確認済み |
| ② 映像 | 完成プレビュー、`visual_assertions` チェックリスト、字幕の誤字 | 全項目にチェック |

- 承認者と日時を記録する(本人のみの利用だが、あとで振り返れるように)。
- 公開後に誤りが見つかった場合は「訂正ログ」に記録し、同じ主張を使う他のプロジェクトに警告を出す(主張は再利用されるため)。

### 4.5 表現のガイドライン(台本生成プロンプトに組み込む)

- 断定は出典がある範囲だけ。「〜と言われています」でぼかさない(ぼかすなら言わない)。
- 「なぜ / 何が違う / どう進化した」の 1 問に 1 本で答える。欲張らない。
- 数値は単位つき、比較は同じ条件で。
- 安全に関わる題材は「自分で判断せず専門家へ」の一文を末尾に自動で付ける。

## 6. 絵コンテ(ショットリスト)データモデル

```jsonc
{
  "id": "exp_01J...",
  "title": "土砂崩れを防ぐ壁の違い",
  "format": { "width": 1080, "height": 1920, "fps": 30, "target_sec": 55 },
  "brand": "brand_default",
  "script": [
    { "id": "ln_01", "kind": "hook", "text": "家の裏の壁、実は形で強さが全然違います", "claims": [] },
    { "id": "ln_02", "kind": "fact", "text": "L 型擁壁は、底版に載った土の重さで倒れにくくなります", "claims": ["clm_07"] }
  ],
  "shots": [
    {
      "id": "sh_04",
      "lines": ["ln_02"],                      // このショット中に流れるナレーション
      "method": "diagram3d",                   // diagram3d | genvideo | still | studio
      "template": "cross_section",
      "params": {
        "structure": "l_retaining_wall",
        "dims_m": { "wall_h": 3.0, "base_len": 2.0, "thickness": 0.3 },
        "cut_plane": "x",
        "camera": { "preset": "orbit_in", "from": "front_left", "to": "section" },
        "highlight": ["base_slab", "soil_on_base"],
        "arrows": [ { "kind": "force", "label": "土の重さ", "from": "soil_on_base", "dir": "down" } ]
      },
      "visual_assertions": ["底版が土側に伸びている", "土の重さの矢印が下向き"],
      "duration_sec": "auto",                  // ナレーション長 + 余白
      "status": "pending | rendering | done | stale"
    }
  ]
}
```

- シーン JSON(Studio)と同じく **スキーマバージョンつき**で `packages/schema` に定義する。
- `method: studio` のショットは Studio のシーン ID を参照する。

## 7. 3D 図解テンプレート(Blender)

**LLM は「どのテンプレートを、どのパラメータで」を決めるだけ**で、形・比率・動きは Blender スクリプトが決定的に作る(Studio の「LLM は操作の提案まで」と同じ原則)。

### 7.1 MVP の基本 8 種

| テンプレート | 内容 | 例 |
|---|---|---|
| `cross_section` | 地面・物体を平面で切り、断面を見せる(断面にハッチングまたは素材テクスチャ) | 擁壁と土、壁の中の断熱材、ケーブルの断面 |
| `fracture_collapse` | ひび割れ → 破砕 → 崩壊(Cell Fracture + 剛体シミュレーション)。シードで再現可能 | 石積み壁の崩壊、橋脚の破断 |
| `force_arrows` | 力・流れの矢印をアニメーション(太さ = 大きさ) | 土圧、風圧、電流、水流 |
| `compare_split` | 画面を上下(縦型なので上下)に分割し、2 案を同条件で比較 | 細い銅線 vs 太い銅線、重力式 vs L 型 |
| `evolution_steps` | 同じ場所で A → B → C と形が変わっていく(モーフ / 置き換え) | 壁の進化、道具の変遷 |
| `exploded_view` | 部品が分解して浮き上がり、ラベルが付く | 充電器の中身、蛇口の構造 |
| `zoom_micro` | 外観から内部・微細構造へ寄っていく(段階的に切り替え) | 銅の結晶、繊維の構造 |
| `label_callout` | 引き出し線つきのラベル(日本語、ブランドフォント) | 部品名・寸法の表示 |

### 7.2 共通部品(アセット)
- 地面・土・草・コンクリート・石・金属(銅・鉄・アルミ)・木・水の **プロシージャルマテリアル**(PBR)。
- 家・塀・道路・木・電柱などの **簡易背景キット**(ローポリ、CC0 素材または Forge で生成)。
- 構造物は **寸法パラメータで生成**(L 型擁壁、重力式擁壁、ブロック塀、梁、パイプ、コイル、ケーブル等)。
- 照明は「晴れの屋外」「スタジオ(白背景)」「室内の机上」の 3 種を既定に。

### 7.3 描画設定
- EEVEE、1080×1920、30fps。サンプル数はプレビュー 8 / 本番 32 を既定。
- カメラプリセット: `orbit_in`(回り込みながら寄る)、`dolly_section`(断面へ寄る)、`top_down`、`slow_push`、`compare_pan`。
- 縦型の安全領域(下部 20% は字幕と UI、右端 12% はいいねボタン等)を考慮して被写体を配置する。

### 7.4 自由生成(v1, E-19)
- テンプレートで表せない図解は、LLM が bpy スクリプトを書く。
- 実行はワーカー内の専用サンドボックス(ネットワーク不可、ファイル書き込みは出力ディレクトリのみ、時間制限)。
- 実行後にサムネを撮り、`visual_assertions` と並べて人が確認する。良いものはテンプレートに昇格させる。

## 8. AI 映像ショット

| 方式 | 第一候補 | 代替 | 目安(RTX 3060、フェーズ E0 で実測) |
|---|---|---|---|
| テキスト → 映像(ローカル) | Wan 2.x T2V 1.3B(縦 480×832、約 8GB) | LTX-Video(高速、品質は控えめ) | 5 秒 1 本 10〜15 分(見込み) |
| 画像 → 映像(ローカル) | Wan 2.x I2V(CPU オフロード)/ LTX-Video I2V | — | 5 秒 1 本 15〜40 分(見込み、重い) |
| 外部 API(オプトイン) | Veo / Kling / Runway 等をアダプタで切り替え | — | 数分。従量課金 |
| 高解像度化 | Real-ESRGAN 等で 1080×1920 へ | ffmpeg のスケーリング | 1〜3 分 |

- **AI 映像は「雰囲気カット」に限定**し、構造の説明には使わない(形が正確でないため)。ファクトチェックの `visual_assertions` も付けない。
- 生成は 1 ショットにつき 2〜3 候補を出して選ぶ。不採用は 7 日で削除。
- 外部 API を使う場合は、送信するもの(プロンプト・参照画像)をプロジェクト画面に明示する。
- 案内役キャラを AI 映像で出すと毎回顔が変わるため、**案内役は原則 Studio ショット**(Forge の人型+Mixamo モーション)で作る。

## 9. 音声・字幕・仕上げ

### 9.1 ナレーション
- **VOICEVOX エンジン**(Docker、CPU)。話者・速度(既定 1.15 倍)・抑揚をブランドプリセットに保存。
- `audio_query` の音素タイミングから **文・句ごとの開始/終了時刻** を取り、ショットの長さと字幕の表示タイミングに使う。
- 読み方辞書: 専門用語の読み(擁壁、底版、導体抵抗 など)をプロジェクト横断で登録。
- クレジット表記(「VOICEVOX:キャラ名」)を説明文に自動で入れる(利用規約に従う)。
- 代替: Style-Bert-VITS2(自分の声に近づけたい場合、v1)。

### 9.2 字幕
- ASS 形式で生成し、ffmpeg で焼き込み。
- 句単位で分割(1 行 8〜12 字、最大 2 行)。強調語(主張のキーワード)は色を変える。
- ブランドプリセット例:
  - 「図解」: 上部に固定タイトル帯(黒の極太、白地)+ 字幕は黄色・黒縁。
  - 「シンプル」: 字幕は白・影つき、タイトル帯なし。
- フォントはライセンスが明確なもの(Noto Sans JP、M PLUS 1 など OFL)を同梱する。

### 9.3 BGM・効果音・合成
- BGM / 効果音はローカルライブラリ(CC0 または利用許諾を確認済みのもの)。ナレーション中は自動で -12dB 下げる。
- 崩壊・カチッ・シュッなどの効果音を、テンプレートのイベント(破砕開始、ラベル出現)に自動で合わせる。
- ラウドネスは -14 LUFS に正規化。
- 冒頭 1 秒に問い(つかみ)を必ず置き、最後は問いへの答えで終える(ループ再生されやすくする)。

## 12. 公開・運用上の注意

- **AI 生成の開示**: YouTube は、本物と見分けがつかない合成・改変コンテンツに開示設定を求めている。3D 図解は明らかに CG なので通常は対象外と考えられるが、フォトリアルな AI 映像カットを含む場合は開示する。投稿用メタデータにチェック項目として出す(規約は変わるので、投稿時に最新を確認する)。
- **量産コンテンツの扱い**: YouTube パートナープログラムは、テンプレートの使い回しだけで差のない大量生産コンテンツを収益化の対象外にしている。題材ごとに独自の調査・図解・構成があること(= このモードの主張台帳と図解)が差別化と収益化の両面で効く。
- **著作権**: 他チャンネルの台本・映像・サムネを素材として取り込まない。資料からの引用は台帳の抜粋にとどめ、台本は自分の言葉で書く(LLM にもそう指示する)。
- **専門家確認**: `risk: high` の題材(建築の安全性、電気工事、健康など)は、可能なら有資格者に台本を見てもらう運用を推奨。

## 13. 非機能要件

| 項目 | 目標 |
|---|---|
| 実働時間 | 60 秒 1 本を **人の作業 30 分以内**(資料選び・確認・修正のみ) |
| 待ち時間 | テーマ入力 → 絵コンテまで 5 分以内(LLM)。描画は夜間バッチで 1 本 1〜2 時間以内(RTX 3060、3D 図解中心の場合) |
| 本番描画 | 3D 図解 1080×1920/30fps 10 秒を 15 分以内(EEVEE) |
| 再現性 | 同じ絵コンテ・同じシードで同じ映像になる(破砕シミュレーションもシード固定) |
| 追跡性 | 書き出した動画から、文 → 主張 → 出典を必ずたどれる |
| データ | 書き出し済みプロジェクトは削除しない(訂正対応のため)。中間ファイルは 7 日で削除 |

## 14. ロードマップ
