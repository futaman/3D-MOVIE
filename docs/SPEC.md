# 3D-MOVIE 仕様書(ドラフト v0.2)

プロンプトから 3D モデルアセットを生成し、それを動かして動画にするまでを一気通貫で行う Web アプリ。
**自前 GPU マシン上でセルフホスト**し、**招待した利用者だけ**がブラウザからアクセスする。

## 0. 決定事項(v0.1 からの確定)

| 論点 | 決定 | 影響 |
|---|---|---|
| 提供形態 | Web アプリ。ただし当面は利用者限定(招待制) | 認証は招待コード+メールのアローリストで十分。課金・クォータは後回し |
| 実行基盤 | 自前 GPU マシンでセルフホスト。推論・レンダリングもそこで行う | 外部 3D 生成 API は使わず OSS モデルを採用。ランニングコストは電気代のみ |
| 品質ターゲット | 映像向けだが、ハイポリは不要 | 1 モデル 2〜10 万三角形、2K テクスチャ、PBR。レンダラは Blender EEVEE 中心 |
| 主役アセット | 人型の汎用人間 + さまざまな小物 | リグは **人型(Humanoid)専用**に絞って作り込む。小物はリグなし+アタッチ |
| アプリ構成 | **1 アプリ内の 2 モード**(「作る」Forge / 「動かす」Studio) | 同一ログイン・同一ライブラリ・同一ビューアを共有。URL は `/forge`, `/studio` |

残っている確認事項は 11 章。

---

## 1. ゴールと非ゴール

### ゴール
- 文章と参照画像だけで「人型キャラクター」と「小物」を作り、組み合わせて 15〜60 秒程度の動画を完成させられる。
- すべて手元のマシンで完結し、生成物やプロンプトが外部に出ない。
- 生成 → 修正 → 再生成のループが速い(ドラフト 1〜2 分、仕上げ 5 分以内)。
- 生成物は glTF/GLB で持ち出せ、Blender・Unity・Unreal でも使える。

### 非ゴール(v1 では扱わない)
- フォトリアル VFX 品質、長尺映像。
- 四足・翼など人型以外のリグ付きキャラクター(小物として静的に扱うのは可)。
- 頂点編集などのモデリング機能。
- 不特定多数向けの公開サービス化(課金、スケールアウト)。

---

## 2. ユースケース

代表シナリオ:
1. **Forge** で「黒いコートを着た 30 代の男性、短髪、映像向け、A ポーズ」と入力 → 4 候補生成 → 1 つ選択 → 顔テクスチャだけ再生成 → 自動リグ(人型)→ ポーズ確認 → ライブラリ保存。
2. **Forge** で「古い真鍮のランタン」「木の椅子」を生成 → 小物としてライブラリ保存。
3. **Studio** で新規シーン → 男性・ランタン・椅子を配置 → 「椅子に座ってランタンを持ち上げ、正面を見る」と指示 → カメラ「ローアングルからゆっくり寄る」 → ライト「夕暮れ」 → プレビュー → 1080p/24fps で書き出し。

## 3. 全体アーキテクチャ

すべて 1 台の GPU マシン上の Docker Compose で動かす。外部に出るのは招待ユーザーのブラウザからの HTTPS のみ。

```
 招待ユーザーのブラウザ
        │ HTTPS(Cloudflare Tunnel または Tailscale 経由)
        ▼
┌───────────────────────────────────────────────────────────┐
│ GPU マシン(docker compose)                                  │
│                                                            │
│  ┌──────────────┐   ┌──────────────┐   ┌────────────────┐ │
│  │ web (Next.js)│──▶│ api (FastAPI)│──▶│ postgres       │ │
│  │ /forge       │   │ 認証・アセット  │   │ redis (キュー)  │ │
│  │ /studio      │◀──│ ジョブ・進捗 WS │   │ ローカル FS /   │ │
│  └──────────────┘   └──────┬───────┘   │   MinIO        │ │
│                            │           └────────────────┘ │
│                            ▼                               │
│  ┌──────────────────────────────────────────────────────┐ │
│  │ worker (Python, CUDA)  ※GPU を排他利用、1 ジョブずつ      │ │
│  │  ├ gen3d   : Hunyuan3D 2.x(形状+テクスチャ)            │ │
│  │  ├ rig     : UniRig → Humanoid 標準スケルトンへ正規化      │ │
│  │  ├ motion  : クリップ検索/連結(v0)、MDM 系生成(v1)       │ │
│  │  └ render  : Blender EEVEE ヘッドレス + ffmpeg           │ │
│  └──────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────┘
```

設計方針:
- **GPU は 1 枚前提**。ワーカーは GPU ジョブを直列実行し、モデルのロード/アンロードをジョブ種別ごとに管理する(VRAM 常駐は「直近に使ったモデル 1 つ」まで)。
- **重い処理はすべて非同期ジョブ**。UI は WebSocket で進捗(ステージ名+%)を受け取る。
- **生成エンジンはアダプタ化**(`ShapeProvider`, `TextureProvider`, `RigProvider`, `MotionProvider`, `Renderer`)。モデルの差し替え・比較を容易にする。
- **人型は標準スケルトンに正規化**。生成経路が何であれ、リグ後は同一のボーン名・階層(Mixamo 互換 65 ボーン、VRM 互換ヒューマノイドマッピング)になるため、モーションは常に同じ経路で適用できる。

## 4. Forge モード(アセット生成)

### 4.1 機能要件

| ID | 機能 | 優先度 |
|---|---|---|
| F-1 | テキストプロンプト → 3D(4 候補、シード指定可) | MVP |
| F-2 | 参照画像(1〜4 枚)→ 3D。テキストとの併用可 | MVP |
| F-3 | アセット種別の選択: **人型** / **小物**。種別ごとにプロンプト補強とパイプラインを切り替える | MVP |
| F-4 | スタイルプリセット: リアル寄り / セミリアル / アニメ調 / スタイライズ。ネガティブ指定 | MVP |
| F-5 | 3D プレビュー(回転・ズーム・ワイヤーフレーム・法線・UV・各 PBR チャンネル表示) | MVP |
| F-6 | リテクスチャ(メッシュ固定でテクスチャだけ再生成。プロンプト変更可) | MVP |
| F-7 | 人型の自動リグ + 標準スケルトン正規化 + ウェイト確認(数ポーズのプリセットで確認) | MVP |
| F-8 | 小物のピボット/スケール正規化と **アタッチポイント**(手に持つ位置・向き)の指定 | MVP |
| F-9 | リメッシュ/デシメーション(目標三角形数指定、UV 保持) | v1 |
| F-10 | 部分リテクスチャ(顔・服など領域指定) | v1 |
| F-11 | 表情用ブレンドシェイプの自動生成(まばたき・口の開閉・基本表情 8 種) | v1 |
| F-12 | エクスポート: GLB(MVP)/ FBX, VRM, USDZ(v1) | MVP / v1 |
| F-13 | バージョン履歴・派生ツリー、タグ・検索・コレクション | v1 |
| F-14 | LLM によるプロンプト補助(3D 向け言い換え、種別に応じた定型句の付与) | MVP(簡易)/ v1 |

### 4.2 画面

1. **ライブラリ**(Forge/Studio 共通): サムネグリッド、種別フィルタ(人型 / 小物 / モーション / 環境)、検索。
2. **生成**: 左にプロンプト・種別・スタイル・参照画像・詳細(シード、候補数、三角形数目標)。中央に候補サムネ 4 枚。右に選択候補の 3D プレビュー。
3. **アセット詳細**: ビューア、メタデータ、派生履歴、アクション(リテクスチャ / リグ / アタッチポイント編集 / エクスポート / Studio で開く)。
4. **ジョブ**: 実行中・待機中・完了・失敗、GPU 使用状況、ログ。

### 4.3 生成パイプライン

```
入力 ─▶ [1] プロンプト正規化(LLM、種別に応じた定型句付与。人型は「A ポーズ、正面、全身、単色背景」を強制)
     ─▶ [2] コンセプト画像生成(任意。テキストのみの場合に 1 枚生成して image-to-3D に回すと安定する)
     ─▶ [3] 形状生成(Hunyuan3D 2.x shape)→ 候補 4 つ
     ─▶ [4] テクスチャ生成(Hunyuan3D paint)→ Albedo + 法線、必要に応じ PBR 分離
     ─▶ [5] 後処理: 法線修正、穴埋め、スケール正規化(人型は身長 1.7m 基準、小物は実寸推定)、原点・向き合わせ
     ─▶ [6] 種別別処理:
            人型 → UniRig で自動リグ → 標準スケルトンへリターゲット → ウェイト検証(テストポーズで破綻検出)
            小物 → ピボット推定、アタッチポイント候補の自動提案
     ─▶ [7] GLB 書き出し、サムネ(ターンテーブル GIF 含む)、メタデータ登録
```

各ステージは独立ジョブ。途中からやり直せる([4] のみ再実行 = リテクスチャ、[6] のみ再実行 = リグし直し)。

### 4.4 採用モデル(OSS、セルフホスト)

| 役割 | 第一候補 | 代替 | 備考 |
|---|---|---|---|
| 形状生成 | Hunyuan3D 2.x(shape) | TRELLIS、TripoSG | テキスト・画像両対応。人型の A ポーズ安定性を検証する |
| テクスチャ | Hunyuan3D 2.x(paint) | TEXTure 系、MV 画像 + 投影ベイク | 2K 出力、PBR 分離は後処理 |
| コンセプト画像 | SDXL / FLUX 系(ローカル) | 省略可 | テキストのみ入力の品質安定化用 |
| 自動リグ | UniRig | Make-It-Animatable、Mixamo(手動フォールバック) | 人型専用で評価 |
| LLM | Claude API | ローカル LLM(Qwen 等) | プロンプト整形・シーン操作解釈。外部に出るのはプロンプト文のみ。完全オフライン要件ならローカル LLM |

> 人型の品質が最重要なので、MVP 着手前に **形状生成 2〜3 モデル × リグ 2 手法のベンチ**(同一プロンプト 20 本)を行い、採用を確定する。

### 5.2 画面

```
┌──────────────────────────────────────────────────────────┐
│ ツールバー(保存 / Undo / 再生 / クイック書き出し / 本番レンダリング) │
├──────────┬────────────────────────────────┬──────────────┤
│ アセット   │                                │ プロパティ     │
│ (ライブラリ│        3D ビューポート            │ Transform /   │
│  モーション│                                │ アタッチ /     │
│  カメラ   │                                │ モーション設定 / │
│  ライト)  │                                │ マテリアル      │
├──────────┴────────────────────────────────┴──────────────┤
│ タイムライン(トラック / クリップ / キーフレーム / 再生ヘッド)        │
├──────────────────────────────────────────────────────────┤
│ プロンプトバー:「男が椅子に座ってランタンを持ち上げる。カメラは正面から寄る」│
└──────────────────────────────────────────────────────────┘
```

プロンプトバーは **シーン編集操作を自然言語で受け付ける**。LLM がシーン JSON への差分操作(クリップ追加、アタッチ、カメラキー追加など)に変換し、Undo 可能な編集として適用する。LLM は「操作の提案」までで、幾何計算(位置合わせ、接地、IK)はアプリ側が決定的に行う。

### 5.3 モーションの仕組み(人型専用に最適化)

1. **ライブラリ検索ベース(MVP)**
   - 標準スケルトン向けに整備した 100〜200 クリップ(歩行・走行・待機・座る・立つ・手を振る・持ち上げる・置く・指差す・頷く など)。
   - LLM が指示文を「クリップ列 + 各クリップの長さ・向き・対象物」に分解。アプリが接地・移動量・向きを解決して連結(クロスフェード)。
   - 「物を持ち上げる」等は、小物のアタッチポイントへ手を合わせる **簡易 IK 補正**を行う。
2. **生成モデルベース(v1)**
   - テキスト→モーション(MDM / MotionGPT 系、HumanML3D 準拠)で未知の動きを生成し、SMPL → 標準スケルトンへリターゲット。
   - 生成結果もクリップとしてライブラリに保存・再利用できる。
3. **小物**
   - リグなし。トランスフォームのプロシージャルアニメ(放物線・バウンド・回転・揺れ)と、人型へのアタッチ/デタッチイベントで表現する。

### 5.4 レンダリング

| モード | 実装 | 目安 |
|---|---|---|
| ビューポート(リアルタイム) | Three.js(WebGL2、WebGPU は段階的) | 編集・確認用。見た目は本番の近似 |
| クイック書き出し | ビューポートのフレームを WebCodecs で MP4 化 | 1080p 15 秒を 1 分以内 |
| 本番レンダリング | シーン JSON → Blender(bpy)にインポート → **EEVEE** でレンダリング → ffmpeg | 1080p/24fps 15 秒を 5 分以内(GPU 次第) |

- シーン JSON が唯一の正。Three.js 側と Blender 側の両インポータが同じ JSON を解釈する。ライト・マテリアルのプリセットごとに「見た目の許容差」を検証する。
- 本番は EEVEE を既定とし、被写界深度・モーションブラー・ブルーム・アンビエントオクルージョンをプリセット化。Cycles はオプション(時間がかかる旨を表示)。

## 6. 共通基盤

### 6.1 アセットデータモデル

```jsonc
{
  "id": "ast_01H...",
  "kind": "humanoid | prop | motion | environment | audio",
  "name": "黒コートの男",
  "version": 3,
  "parent_id": "ast_01G...",
  "prompt": { "text": "...", "negative": "...", "style": "semireal", "seed": 1234, "ref_images": ["..."] },
  "pipeline": { "shape": "hunyuan3d-2.1", "texture": "hunyuan3d-paint-2.1", "rig": "unirig-1.0" },
  "files": {
    "glb": "assets/ast_01H.../v3/model.glb",
    "textures": { "albedo": "...", "normal": "...", "orm": "..." },
    "thumbnail": "...", "turntable": "...",
    "source_images": ["..."]
  },
  "stats": { "triangles": 48000, "materials": 2, "texture_size": 2048, "height_m": 1.72 },
  "rig": { "skeleton": "std-humanoid-v1", "bone_count": 65, "blendshapes": ["blink", "jawOpen"] },   // humanoid のみ
  "attach_points": [ { "name": "grip", "bone_hint": "hand_r", "offset": [0,0,0], "rotation": [0,0,0,1] } ], // prop のみ
  "tags": ["character", "male", "coat"],
  "created_at": "...", "owner_id": "..."
}
```

### 6.2 ファイル形式と規約
- 正は **glTF 2.0 / GLB**。PBR(metal/rough)、スキン、ブレンドシェイプ、アニメーションを格納。
- **標準スケルトン `std-humanoid-v1`**: Mixamo 互換のボーン名・階層、Y-up、身長 1.7m 基準の T/A ポーズ。VRM ヒューマノイドへのマッピング表を同梱。
- モーションはボーンのみの GLB として保存。すべて `std-humanoid-v1` 前提。
- シーンは独自 JSON(スキーマバージョン付き)。

### 6.3 ジョブ管理
- 種別: `generate_shape`, `generate_texture`, `postprocess`, `rig`, `generate_motion`, `render_video`。
- 状態: `queued → running → succeeded | failed | canceled`。ステージ名と進捗率、推定残り時間、VRAM 使用量を持つ。
- GPU ジョブは直列。CPU のみのジョブ(後処理、サムネ、ffmpeg)は並列可。
- WebSocket で進捗配信。失敗は原因分類(OOM / モデルエラー / タイムアウト / 入力不正)を返し、OOM 時は自動で低解像度設定を提案。

### 6.4 認証とアクセス制御(招待制)
- 管理者が招待コードを発行(有効期限・回数制限付き)。
- ログインはメールのマジックリンクまたは Passkey。パスワードは持たない。
- アローリスト外のメールは登録不可。ロールは `admin` / `member`。
- アセットはユーザーごとに所有。`shared` フラグで全メンバーに公開可。
- 外部公開は Cloudflare Tunnel(Access で追加の認証も可)または Tailscale(メンバーがインストール可能なら最も簡単)。

### 6.5 ストレージ
- 生成物はローカルディスク(`/data/assets`)に保存。S3 互換が必要になった時点で MinIO に切り替えられるよう、ストレージ層をインターフェース化。
- 中間成果物(候補 4 つの未採用分、マルチビュー画像)は 7 日で自動削除(採用したものは保持)。
- 日次でメタデータ DB と `/data/assets` を外部ディスクへバックアップ。

## 7. 技術スタック

| レイヤ | 採用 | 理由 |
|---|---|---|
| フロント | Next.js(App Router)+ TypeScript、React Three Fiber + drei、Zustand、Tailwind | Three.js エコシステム、1 アプリ 2 モードの実装が容易 |
| タイムライン | 自作(Canvas ベース)。theatre.js は参考 | 要件が独自(クリップ連結・アタッチイベント) |
| API | **FastAPI(Python)** | ワーカーと言語・型定義(Pydantic)を共有できる |
| ワーカー | Python、PyTorch + CUDA、Blender(bpy / headless)、ffmpeg | 推論・レンダリングがすべて Python から扱える |
| キュー | Redis + RQ(または arq) | 単一マシンなら十分。Celery は過剰 |
| DB | PostgreSQL | 派生履歴・検索に十分 |
| 認証 | 自前(マジックリンク + Passkey)または Authentik | 招待制の小規模運用 |
| LLM | Claude API(プロンプト整形・シーン操作解釈・クリップ選択) | 構造化出力(JSON)の信頼性 |
| 配信 | Cloudflare Tunnel または Tailscale | ポート開放不要 |
| 実行 | Docker Compose(NVIDIA Container Toolkit) | GPU マシン 1 台で完結 |

## 8. ハードウェア前提(要確認)

| 構成 | 推奨 | 最低 |
|---|---|---|
| GPU VRAM | **24GB**(RTX 3090 / 4090 / A5000 クラス) | 12GB(形状とテクスチャを別ジョブに分け、解像度を落とす) |
| システム RAM | 64GB | 32GB |
| ストレージ | NVMe 1TB 以上(モデル重み約 30〜50GB + アセット) | 500GB |
| OS | Linux(Ubuntu 22.04/24.04)+ NVIDIA ドライバ + Docker | Windows は WSL2 経由で動作見込み(要検証) |

VRAM 24GB なら Hunyuan3D shape+paint を同時常駐でき、生成 1 回(4 候補)を 2〜3 分で回せる見込み。12GB ではモデルのロード/アンロードが毎回入り、5〜8 分程度になる。

## 9. 非機能要件

| 項目 | 目標 |
|---|---|
| 生成レイテンシ | テキスト → 4 候補プレビュー 3 分以内(24GB)、人型リグ込み 6 分以内 |
| 本番レンダリング | 1080p/24fps 15 秒を 5 分以内(EEVEE) |
| 同時利用 | 招待ユーザー 5〜10 名。GPU ジョブはキュー待ち(待ち順と推定時間を表示) |

| 復旧 | ワーカー異常終了時にジョブを自動再キュー(最大 2 回)、日次バックアップ |

## 10. ロードマップ

### フェーズ 0: 技術検証(2〜3 週間)
- GPU マシンで Hunyuan3D 2.x / TRELLIS を動かし、人型 A ポーズ・小物の品質と所要時間を比較(同一プロンプト 20 本)。
- UniRig で人型 10 体をリグし、標準スケルトンへ正規化できるか・Mixamo クリップで破綻しないかを確認。

## 11. 残っている確認事項

1. **GPU の型番と VRAM**(8 章の前提確認。12GB 以下なら MVP の機能構成を見直す)。
2. **GPU マシンの OS**(Linux か Windows か。Windows なら WSL2 + Docker Desktop で進める)。
3. **想定利用者数と、Tailscale のインストールを頼めるか**(頼めるなら Tailscale が最も簡単。無理なら Cloudflare Tunnel)。
4. **LLM に外部 API(Claude)を使ってよいか**(プロンプト文のみ外部送信される。完全オフラインが必要ならローカル LLM)。
5. **モーションライブラリの出所**(Mixamo はライセンス上「自作コンテンツへの利用」は可だが再配布不可。各利用者が自分でダウンロードする運用か、CC0 のライブラリを集めるか)。
