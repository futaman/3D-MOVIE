# 3D-MOVIE 仕様書(v1.0)

> v1.0 = 要件・構成の確定版。所要時間・採用モデルの数値はフェーズ 0 の実測後に更新する。

プロンプトから 3D モデルアセットを生成し、それを動かして動画にするまでを一気通貫で行う Web アプリ。
**自分の Windows デスクトップ PC(RTX 3060 12GB / RAM 48GB)上で動かし、同じ PC のブラウザから自分だけが使う**個人用ツール。

## 0. 決定事項

| 論点 | 決定 | 影響 |
|---|---|---|
| 提供形態 | Web アプリ(ブラウザ UI)。利用者は **本人のみ、同じデスクトップ PC から** | 認証・招待・マルチユーザー機能は作らない。`localhost` にのみバインドし、外部からは到達不能 |
| 実行基盤 | **Windows デスクトップ、RTX 3060 12GB、RAM 48GB**。WSL2(Ubuntu)+ Docker Desktop | OSS モデルを **12GB に収まる構成**で選定し、余裕のある RAM へ CPU オフロードする。形状・テクスチャ・レンダリングは別ジョブにして VRAM を順番に使う |
| LLM | **Claude API を使用** | プロンプト整形・シーン操作解釈・クリップ選択に利用。外部に出るのはプロンプト文のみ |
| モーション素材 | **Mixamo を主軸**、不足分は CMU モーションキャプチャ DB | 本人利用のみなので Mixamo の「再配布不可」条項に抵触しない。自分の Adobe アカウント(無料)で取得して取り込む |
| 開発者の環境経験 | WSL2 / Docker は **未経験** | セットアップ手順書 [SETUP_WINDOWS.md](SETUP_WINDOWS.md) をフェーズ 0 の最初に実施。Docker Desktop(GUI あり)を採用し、コマンドは最小限にする |
| 品質ターゲット | 映像向けだが、ハイポリは不要 | 1 モデル 2〜10 万三角形、2K テクスチャ、PBR。レンダラは Blender EEVEE 中心 |
| 主役アセット | 人型の汎用人間 + さまざまな小物 | リグは **人型(Humanoid)専用**に絞って作り込む。小物はリグなし+アタッチ |
| アプリ構成 | **1 アプリ内の 2 モード**(「作る」Forge / 「動かす」Studio) | 同一ライブラリ・同一ビューアを共有。URL は `/forge`, `/studio` |

残っている確認事項は 11 章。

## 1. ゴールと非ゴール

### ゴール
- 文章と参照画像だけで「人型キャラクター」と「小物」を作り、組み合わせて 15〜60 秒程度の動画を完成させられる。
- すべて手元の PC で完結し、生成物が外部に出ない(外部送信は Claude API へのプロンプト文のみ)。
- 生成 → 修正 → 再生成のループが現実的な速さで回る(RTX 3060 で形状 4 候補 5〜8 分、テクスチャ込みの仕上げ 15 分以内)。
- 生成物は glTF/GLB で持ち出せ、Blender・Unity・Unreal でも使える。

### 非ゴール(v1 では扱わない)
- フォトリアル VFX 品質、長尺映像。
- 四足・翼など人型以外のリグ付きキャラクター(小物として静的に扱うのは可)。
- 頂点編集などのモデリング機能。
- 他人への提供(マルチユーザー、招待、課金、スケールアウト)。将来必要になったら 6.4 の設計を拡張する。

## 2. ユースケース

代表シナリオ:
1. **Forge** で「黒いコートを着た 30 代の男性、短髪、映像向け、A ポーズ」と入力 → 4 候補生成 → 1 つ選択 → 顔テクスチャだけ再生成 → 自動リグ(人型)→ ポーズ確認 → ライブラリ保存。
2. **Forge** で「古い真鍮のランタン」「木の椅子」を生成 → 小物としてライブラリ保存。
3. **Studio** で新規シーン → 男性・ランタン・椅子を配置 → 「椅子に座ってランタンを持ち上げ、正面を見る」と指示 → カメラ「ローアングルからゆっくり寄る」 → ライト「夕暮れ」 → プレビュー → 1080p/24fps で書き出し。

## 3. 全体アーキテクチャ

Windows PC 上の WSL2(Ubuntu)で Docker Desktop(Compose)を動かす。ブラウザは同じ PC の `http://localhost:3000` でアクセスする。

```
 同じ PC のブラウザ(Chrome / Edge)
        │ http://localhost:3000
        ▼
┌───────────────────────────────────────────────────────────┐
│ Windows PC ─ WSL2 (Ubuntu) ─ docker compose                 │
│                                                            │
│  ┌──────────────┐   ┌──────────────┐   ┌────────────────┐ │
│  │ web (Next.js)│──▶│ api (FastAPI)│──▶│ postgres       │ │
│  │ /forge       │   │ アセット・ジョブ │   │ redis (キュー)  │ │
│  │ /studio      │◀──│ ジョブ・進捗 WS │   │ ローカル FS /   │ │
│  └──────────────┘   └──────┬───────┘   │   MinIO        │ │
│                            │           └────────────────┘ │
│                            ▼                               │
│  ┌──────────────────────────────────────────────────────┐ │
│  │ worker (Python, CUDA)  ※RTX 3060 12GB を排他利用、1 ジョブずつ │ │
│  │  ├ gen3d   : Hunyuan3D 2(低 VRAM モード、形状→テクスチャ順) │ │
│  │  ├ rig     : UniRig → Humanoid 標準スケルトンへ正規化      │ │
│  │  ├ motion  : クリップ検索/連結(v0)、MDM 系生成(v1)       │ │
│  │  └ render  : Blender EEVEE ヘッドレス + ffmpeg           │ │
│  └──────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────┘
```

設計方針:
- **GPU は 1 枚・12GB 前提**。ワーカーは GPU ジョブを直列実行し、**ステージごとにモデルをロード/アンロード**する(形状モデルとテクスチャモデルを同時に VRAM に置かない)。常駐は「直近に使ったモデル 1 つ」まで。
- **Blender レンダリングと AI 推論は同時に走らせない**。レンダリングも GPU ジョブとしてキューに乗せる。
- **ブラウザのビューポートも同じ GPU を使う**ため、重い生成中はビューポートの描画品質を自動で落とす(影・ポストエフェクトを OFF)。
- **重い処理はすべて非同期ジョブ**。UI は WebSocket で進捗(ステージ名+%)を受け取る。
- **生成エンジンはアダプタ化**(`ShapeProvider`, `TextureProvider`, `RigProvider`, `MotionProvider`, `Renderer`)。モデルの差し替え・比較を容易にする。
- **人型は標準スケルトンに正規化**。生成経路が何であれ、リグ後は同一のボーン名・階層(Mixamo 互換 65 ボーン、VRM 互換ヒューマノイドマッピング)になるため、モーションは常に同じ経路で適用できる。

| F-9 | リメッシュ/デシメーション(目標三角形数指定、UV 保持) | v1 |

| F-11 | 表情用ブレンドシェイプの自動生成(まばたき・口の開閉・基本表情 8 種) | v1 |
| F-12 | エクスポート: GLB(MVP)/ FBX, VRM, USDZ(v1) | MVP / v1 |
| F-13 | バージョン履歴・派生ツリー、タグ・検索・コレクション | v1 |

### 4.2 画面

1. **ライブラリ**(Forge/Studio 共通): サムネグリッド、種別フィルタ(人型 / 小物 / モーション / 環境)、検索。
2. **生成**: 左にプロンプト・種別・スタイル・参照画像・詳細(シード、候補数、三角形数目標)。中央に候補サムネ 4 枚。右に選択候補の 3D プレビュー。
3. **アセット詳細**: ビューア、メタデータ、派生履歴、アクション(リテクスチャ / リグ / アタッチポイント編集 / エクスポート / Studio で開く)。
4. **ジョブ**: 実行中・待機中・完了・失敗、GPU 使用状況、ログ。

### 4.3 生成パイプライン

```
入力 ─▶ [1] プロンプト正規化(LLM、種別に応じた定型句付与。人型は「A ポーズ、正面、全身、単色背景」を強制)
     ─▶ [2] コンセプト画像生成(テキストのみの場合。SDXL-Turbo / FLUX schnell(FP8)で 1 枚生成し image-to-3D に回す。生成後すぐアンロード)
     ─▶ [3] 形状生成(Hunyuan3D 2 shape、低 VRAM モード)→ 候補 4 つ(テクスチャなしで先にプレビュー表示)
     ─▶ [4] テクスチャ生成(Hunyuan3D 2 paint、**ユーザーが選んだ候補のみ**)→ Albedo + 法線、必要に応じ PBR 分離
     ─▶ [5] 後処理: 法線修正、穴埋め、スケール正規化(人型は身長 1.7m 基準、小物は実寸推定)、原点・向き合わせ
     ─▶ [6] 種別別処理:
            人型 → UniRig で自動リグ → 標準スケルトンへリターゲット → ウェイト検証(テストポーズで破綻検出)
            小物 → ピボット推定、アタッチポイント候補の自動提案
     ─▶ [7] GLB 書き出し、サムネ(ターンテーブル GIF 含む)、メタデータ登録
```

各ステージは独立ジョブ。途中からやり直せる([4] のみ再実行 = リテクスチャ、[6] のみ再実行 = リグし直し)。

### 4.4 採用モデル(OSS、セルフホスト)

12GB に収めることを最優先に選ぶ。VRAM の目安は公称値と報告値をもとにした見込みで、フェーズ 0 で実測する。

| 役割 | 第一候補 | 代替 | VRAM 目安 | 備考 |
|---|---|---|---|---|
| 形状生成 | Hunyuan3D 2 shape(低 VRAM モード、FP16 + CPU オフロード) | Hunyuan3D-2mini(0.6B、約 5GB)、TripoSR(約 6GB、品質は落ちる) | 約 8〜11GB | TRELLIS は 16GB 推奨のため **候補から外す**。RAM 48GB なので重みの CPU オフロードは余裕がある |
| テクスチャ | Hunyuan3D 2 paint(低 VRAM モード、解像度 1K→後処理で 2K 化) | マルチビュー画像 + Blender 投影ベイク | 約 10〜12GB | 形状をアンロードしてから実行。OOM 時は自動で 512px に落として再試行 |
| コンセプト画像 | SDXL-Turbo(FP16) | FLUX.1 schnell(重い。3060 では 1 枚 1 分超) | 約 6〜8GB | テキストのみ入力の品質安定化用。1 枚生成して即アンロード |
| 自動リグ | UniRig | Make-It-Animatable、Mixamo 自動リグ(Web で手動、フォールバック) | 約 4〜6GB | 人型専用で評価 |
| LLM | Claude API(確定) | — | 0 | プロンプト整形・シーン操作解釈・クリップ選択。構造化出力(JSON)を使う |

> 人型の品質が最重要なので、MVP 着手前に **形状生成 2〜3 モデル × リグ 2 手法のベンチ**(同一プロンプト 20 本)を行い、12GB での所要時間と OOM の有無を実測して採用を確定する。

### 5.2 画面

```
┌──────────────────────────────────────────────────────────┐
│ ツールバー(保存 / Undo / 再生 / クイック書き出し / 本番レンダリング) │
├──────────┬────────────────────────────────┬──────────────┤
│ アセット   │                                │ プロパティ     │
│ (ライブラリ│        3D ビューポート            │ Transform /   │
│  モーション│                                │ アタッチ /     │
│  カメラ   │                                │ モーション設定 / │
│  ライト)  │                                │ マテリアル      │
├──────────┴────────────────────────────────┴──────────────┤
│ タイムライン(トラック / クリップ / キーフレーム / 再生ヘッド)        │
├──────────────────────────────────────────────────────────┤
│ プロンプトバー:「男が椅子に座ってランタンを持ち上げる。カメラは正面から寄る」│
└──────────────────────────────────────────────────────────┘
```

プロンプトバーは **シーン編集操作を自然言語で受け付ける**。LLM がシーン JSON への差分操作(クリップ追加、アタッチ、カメラキー追加など)に変換し、Undo 可能な編集として適用する。LLM は「操作の提案」までで、幾何計算(位置合わせ、接地、IK)はアプリ側が決定的に行う。

### 5.3 モーションの仕組み(人型専用に最適化)

1. **ライブラリ検索ベース(MVP)**
   - 標準スケルトン向けに整備した 100〜200 クリップ(歩行・走行・待機・座る・立つ・手を振る・持ち上げる・置く・指差す・頷く など)。
   - 出所は **Mixamo**(自分の Adobe アカウントでまとめてダウンロードし、FBX → GLB 変換して取り込む「インポートウィザード」を用意する)。足りない動きは **CMU モーションキャプチャ DB**(BVH、無償)をリターゲットして補う。Mixamo はもともと標準スケルトンと同じボーン構成なので変換コストがほぼない。
   - LLM が指示文を「クリップ列 + 各クリップの長さ・向き・対象物」に分解。アプリが接地・移動量・向きを解決して連結(クロスフェード)。
   - 「物を持ち上げる」等は、小物のアタッチポイントへ手を合わせる **簡易 IK 補正**を行う。
2. **生成モデルベース(v1)**
   - テキスト→モーション(MDM / MotionGPT 系、HumanML3D 準拠)で未知の動きを生成し、SMPL → 標準スケルトンへリターゲット。
   - 生成結果もクリップとしてライブラリに保存・再利用できる。
3. **小物**
   - リグなし。トランスフォームのプロシージャルアニメ(放物線・バウンド・回転・揺れ)と、人型へのアタッチ/デタッチイベントで表現する。

### 5.4 レンダリング

| モード | 実装 | 目安 |
|---|---|---|
| ビューポート(リアルタイム) | Three.js(WebGL2、WebGPU は段階的) | 編集・確認用。見た目は本番の近似 |
| クイック書き出し | ビューポートのフレームを WebCodecs で MP4 化 | 1080p 15 秒を 1 分以内 |
| 本番レンダリング | シーン JSON → Blender(bpy)にインポート → **EEVEE** でレンダリング → ffmpeg | 1080p/24fps 15 秒を 5 分以内(GPU 次第) |

- シーン JSON が唯一の正。Three.js 側と Blender 側の両インポータが同じ JSON を解釈する。ライト・マテリアルのプリセットごとに「見た目の許容差」を検証する。
- 本番は EEVEE を既定とし、被写界深度・モーションブラー・ブルーム・アンビエントオクルージョンをプリセット化。Cycles はオプション(時間がかかる旨を表示)。

### 6.1 アセットデータモデル

```jsonc

  "pipeline": { "shape": "hunyuan3d-2.1", "texture": "hunyuan3d-paint-2.1", "rig": "unirig-1.0" },
  "files": {
```

### 6.2 ファイル形式と規約
- 正は **glTF 2.0 / GLB**。PBR(metal/rough)、スキン、ブレンドシェイプ、アニメーションを格納。
- **標準スケルトン `std-humanoid-v1`**: Mixamo 互換のボーン名・階層、Y-up、身長 1.7m 基準の T/A ポーズ。VRM ヒューマノイドへのマッピング表を同梱。
- モーションはボーンのみの GLB として保存。すべて `std-humanoid-v1` 前提。
- シーンは独自 JSON(スキーマバージョン付き)。

### 6.3 ジョブ管理
- 種別: `generate_shape`, `generate_texture`, `postprocess`, `rig`, `generate_motion`, `render_video`。
- 状態: `queued → running → succeeded | failed | canceled`。ステージ名と進捗率、推定残り時間、VRAM 使用量を持つ。
- GPU ジョブは直列。CPU のみのジョブ(後処理、サムネ、ffmpeg)は並列可。
- WebSocket で進捗配信。失敗は原因分類(OOM / モデルエラー / タイムアウト / 入力不正)を返し、OOM 時は自動で低解像度設定を提案。

### 6.4 認証とアクセス(本人のみ・同一 PC)
- **認証なし**。web / api のポートは `127.0.0.1` にのみバインドし、LAN や外部から到達できないようにする。
- 将来、別端末から使いたくなった場合は Tailscale + 単一パスワードを追加する(設計上は環境変数 1 つで有効化できる形にしておく)。
- データモデルの `owner_id` は残す(将来マルチユーザー化する際に移行しやすい)が、UI・API には出さない。

### 6.5 ストレージ
- 生成物はローカルディスク(`/data/assets`)に保存。S3 互換が必要になった時点で MinIO に切り替えられるよう、ストレージ層をインターフェース化。
- 中間成果物(候補 4 つの未採用分、マルチビュー画像)は 7 日で自動削除(採用したものは保持)。
- 週次でメタデータ DB と `/data/assets` を外部ディスク(または Windows 側のドライブ)へバックアップ。
- WSL2 のディスク I/O 性能のため、`/data` は **WSL2 内の ext4 上**に置く(Windows 側の `/mnt/c` にマウントしない)。エクスポート時だけ Windows 側へコピーする。

## 8. ハードウェア前提と 12GB 運用方針

### 8.1 実機(確定)

| 構成 | 実機 | 備考 |
|---|---|---|
| GPU | **NVIDIA RTX 3060 12GB**(Ampere、CUDA コア 3584、メモリ帯域 360GB/s) | FP16 / INT8 は高速。**FP8 はハードウェア非対応**なので量子化は INT8(bitsandbytes)か FP16 + CPU オフロードで行う。4070 比でおよそ 0.6 倍の速度 |
| OS | **Windows(デスクトップ)** | WSL2(Ubuntu 24.04)+ Docker Desktop。NVIDIA ドライバは Windows 側のみ(WSL2 内にドライバを入れてはいけない) |
| システム RAM | **48GB** | WSL2 に 32GB を割り当て(`.wslconfig`)。モデル重みの CPU オフロードに十分 |
| ストレージ | WSL2 用に NVMe 300GB 以上を確保(要確認) | モデル重み約 30GB + Docker イメージ約 30GB + Blender + アセット。WSL2 の仮想ディスクは既定で C: に置かれるので空き容量に注意 |

### 8.2 12GB で成立させるための方針

1. **ステージ分離とアンロード**: 画像生成 → 形状 → テクスチャ → リグ → レンダリングを別ジョブにし、各ステージ終了時に VRAM を解放する。
2. **候補 4 つはテクスチャなしで先に見せる**: 形状だけなら 1 候補 30〜60 秒。ユーザーが選んだ 1 つだけテクスチャを生成して時間と VRAM を節約する。
3. **解像度の自動フォールバック**: OOM を検知したらテクスチャ解像度やオクトリー解像度を一段落として自動再試行し、UI に「低解像度で生成しました」と表示する。
4. **FP16 既定、必要なら INT8**: RTX 3060 は FP8 非対応のため、量子化する場合は INT8(bitsandbytes)。品質差を検証した上で導入する。
5. **Blender は EEVEE**: 1080p でも VRAM 3〜4GB 程度。Cycles は OptiX で 12GB でも可だが、推論と同時には走らせない。
6. **ビューポートの省電力モード**: GPU ジョブ実行中はブラウザ側の描画負荷を下げる。

### 8.3 RTX 3060 での見込み所要時間(フェーズ 0 で実測して更新)

| 処理 | 見込み |
|---|---|
| コンセプト画像 1 枚(SDXL-Turbo) | 10〜20 秒 |
| 形状生成 1 候補(Hunyuan3D 2 shape、低 VRAM) | 60〜120 秒 → 4 候補で 5〜8 分 |
| テクスチャ生成 1 体(Hunyuan3D 2 paint、1K) | 4〜6 分 |
| 自動リグ 1 体(UniRig) | 1〜2 分 |
| **人型 1 体を完成させる合計** | **12〜18 分**(候補選択の待ち時間を除く) |
| 本番レンダリング 1080p/24fps 15 秒(EEVEE、360 フレーム) | 10〜20 分(1 フレーム 2〜3 秒) |
| クイック書き出し(ブラウザ) | 1〜2 分 |

長めなので、**ジョブ完了時にブラウザ通知を出す**こと、**生成中も Studio で編集を続けられる**ことを MVP の必須要件とする。
